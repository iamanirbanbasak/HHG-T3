Reverse-image search & face verification
Every candidate independently re-embedded and scored
Why this matters: a plain image lookup returns anything visually similar. Here, every candidate URL is fetched, its face is detected and embedded independently, then scored against the probe by cosine similarity. The search provider proposes — the embedding disposes.

3
Evidence bundle
Canonical JSON fingerprinting the match — what gets hashed
What is stored: a canonical JSON document containing SHA-256 digests of the probe image, aligned face crop, candidate image, and post text — plus the cosine score, URL, platform, and timestamp. No raw images are put on-chain, only their digests. Altering any source file changes the bundle hash.
4
Anchor on-chain
keccak256(bundle) stored in FaceMatchRegistry via a signed tx
What is anchored: the keccak256 hash of the canonical bundle is written to a minimal, append-only Solidity contract (FaceMatchRegistry.anchor()). The contract has no update or delete path — once recorded, the record cannot be changed.
5
Re-verification
Read hash from chain, recompute from local files — compare
How it works: the verifier performs two independent operations: (1) reads evidenceHash from the chain via eth_call, and (2) recomputes the hash from the local artifact files on disk. These two paths never share a stored digest — the comparison is genuine.
6
Tamper demonstration
Prove the chain detects any alteration of the evidence
The test: one byte of the post-text source file is flipped in a temporary copy. The bundle is recomputed from the mutated file — the hash changes. The on-chain hash is unchanged. The mismatch is detected. This proves the system cannot be fooled by editing evidence after the fact.
A cosine score is not a probability and not a confidence percentage. A match above threshold is evidence of a probable match, not an identification. The blockchain proves when a claim was recorded and that it has not changed since — it does not prove the claim is true.
